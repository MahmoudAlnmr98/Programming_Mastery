# Classical AUTOSAR: من الصفر إلى الاحتراف

> هذا الدليل مبني على فكرة واحدة:
> كل نظام معقد في السيارات هو في النهاية مجموعة طبقات بسيطة فوق بعض.
> سنبنيها واحدة واحدة حتى تصبح قادراً على فهم وتصميم برمجيات السيارات.

---

## الجزء الأول: لماذا AUTOSAR؟

### ابدأ من هنا

تخيل أنك تعمل في شركة تصنع سيارات.

كل سيارة فيها مئات الوحدات الإلكترونية.

كل وحدة تحتاج برنامجاً.

```
السيارة القديمة:
↓
كل مورّد يكتب كوداً مختلفاً
↓
تغيير قطعة واحدة يعني إعادة كتابة كل شيء
↓
تكلفة هائلة + وقت ضائع
```

بعد ظهور AUTOSAR:

```
كل المورّدين يتكلمون نفس اللغة
↓
تبادل الكود بسهولة
↓
تركيز على الوظيفة لا على التفاصيل
↓
سيارات أكثر أماناً وأسرع تطويراً
```

لماذا؟

لأن صناعة السيارات احتاجت معياراً موحداً لبرمجة السيارات.

---

### ما هو AUTOSAR؟

AUTOSAR = AUTomotive Open System ARchitecture  
(معمارية النظام المفتوح للسيارات).

هو معيار دولي لبرمجة وحدات التحكم الإلكترونية في السيارات.

```
أُسِّس عام 2003 من تحالف كبار صانعي السيارات:
BMW  ← بي إم دبليو
Bosch ← بوش
Continental ← كونتيننتال
Daimler ← دايملر
Ford ← فورد
GM ← جنرال موتورز
PSA ← بيجو سيتروين
Siemens ← سيمنز
Toyota ← تويوتا
Volkswagen ← فولكسفاغن
... وعشرات غيرهم
```

الهدف:

```
- توحيد كيفية كتابة برمجيات السيارات
- الفصل بين البرمجيات والعتاد
- إمكانية إعادة استخدام الكود بين شركات مختلفة
- تسهيل الصيانة والتطوير
```

---

### نوعان رئيسيان من AUTOSAR

```
AUTOSAR
    │
    ├── Classical AUTOSAR (CP)
    │   ← للأنظمة المحدودة الموارد
    │   ← الوحدات التقليدية كالمحرك والفرامل
    │   ← هذا ما سندرسه
    │
    └── Adaptive AUTOSAR (AP)
        ← للأنظمة الحديثة المعقدة
        ← السيارات ذاتية القيادة والتحديثات OTA
        ← يعمل فوق نظام تشغيل POSIX مثل Linux
```

---

### الأسئلة الثلاث الكبرى

**أولاً: كيف يتواصل كود المحرك مع كود الفرامل؟**

أحد يعمل على BMW، آخر يعمل على Continental.
هل يمكنهم التواصل دون أن يعرف كل منهم تفاصيل الآخر؟

**ثانياً: كيف تضمن أمان السيارة برمجياً؟**

خطأ في برنامج الفرامل يمكن أن يقتل إنساناً.
كيف تبني نظاماً برمجياً موثوقاً بدرجة جراحية؟

**ثالثاً: كيف تبدّل مورّداً دون تغيير كل الكود؟**

قررت تغيير مورّد حساس الضغط.
هل ستُعيد كتابة كل كود السيارة؟

AUTOSAR يجيب على الثلاثة.

## الجزء الثاني: اللبنات الأساسية

### الخطوة الأولى: ECU (وحدة التحكم الإلكترونية)

هذه أساس كل شيء في السيارة الحديثة.

ECU = Electronic Control Unit (وحدة التحكم الإلكترونية).

تخيل أنك في مدينة ذكية.

```
المدينة   = السيارة
المباني   = وحدات ECU
الطرق     = الشبكة (CAN/LIN/Ethernet)
المسؤولون = البرامج داخل كل مبنى
```

في سيارة حديثة قد يكون هناك:

```
أكثر من 100 ECU مختلفة مثل:
- ECU المحرك (Engine Control Unit)
- ECU ناقل الحركة (Transmission Control Unit)
- ECU الفرامل (Brake Control Unit / ABS / ESP)
- ECU الوسائد الهوائية (Airbag Control Unit)
- ECU نظام القيادة (Steering Control Unit)
- ECU التكييف (HVAC Control Unit)
- ECU المصابيح (Body Control Module)
- ECU الشاشة (Infotainment Control Unit)
... وعشرات غيرها
```

كل ECU هو في الأساس:

```
┌──────────────────────────────────────┐
│              ECU                     │
│  ┌────────────────────────────────┐  │
│  │  Microcontroller (MCU)         │  │
│  │  المتحكم الدقيق               │  │
│  └────────────────────────────────┘  │
│  ┌────────────────────────────────┐  │
│  │  Flash Memory                  │  │
│  │  ذاكرة البرنامج                │  │
│  └────────────────────────────────┘  │
│  ┌────────────────────────────────┐  │
│  │  RAM                           │  │
│  │  ذاكرة التشغيل                 │  │
│  └────────────────────────────────┘  │
│  ┌────────────────────────────────┐  │
│  │  Connectors                    │  │
│  │  موصلات للحساسات والمشغلات      │  │
│  └────────────────────────────────┘  │
└──────────────────────────────────────┘
```

---

### الخطوة الثانية: بروتوكولات الاتصال في السيارة

كيف تتحدث ECUs مع بعضها؟

تخيل موظفين في نفس الشركة لكن في مكاتب مختلفة.

```
يتواصلون عبر:
- هاتف (CAN Bus) ← للرسائل العاجلة
- إيميل (LIN Bus) ← للرسائل البطيئة الرخيصة
- شبكة سريعة (Ethernet/FlexRay) ← للبيانات الكبيرة
```

**1. CAN (Controller Area Network / شبكة منطقة التحكم):**

```
الأكثر شيوعاً في السيارات منذ 1986
السرعة: حتى 1 Mbps
يعمل على سلكين فقط: CAN-High و CAN-Low
يدعم حتى 127 عقدة على نفس الشبكة
مثال للاستخدام: ECU المحرك يرسل سرعة الدوران لـ ECU ناقل الحركة
```

كيف يعمل CAN:

```
ECU A يريد إرسال رسالة:
    │
    ▼
يضع الرسالة على الشبكة مع معرّف (ID)
    │
    ▼
كل ECU على الشبكة يرى الرسالة
    │
    ▼
فقط من يهتم بهذا الـ ID يقرأ الرسالة
    │
    ▼
البقية يتجاهلونها
```

هذا يسمى: Broadcast Communication (الاتصال البث).

**2. LIN (Local Interconnect Network / شبكة التوصيل المحلية):**

```
أبطأ وأرخص من CAN
السرعة: حتى 20 Kbps
سلك واحد فقط
عبارة عن Master يسأل وعدة Slaves يردون
مثال للاستخدام: حساسات المطر، نوافذ السيارة، مقاعد
```

**3. FlexRay:**

```
أسرع من CAN وأكثر حتمية
السرعة: حتى 10 Mbps
مضمون في الوقت
يُستخدم في أنظمة الأمان الحرجة مثل X-by-Wire
```

**4. Automotive Ethernet:**

```
يصل إلى 1 Gbps و 10 Gbps
للأنظمة الحديثة: كاميرات، رادار، ADAS
يكتسح الصناعة بسرعة
```

### الخطوة الثالثة: ما قبل AUTOSAR

قبل أن نفهم AUTOSAR يجب أن نفهم المشكلة التي حلّها.

**المشكلة الكلاسيكية:**

```
شركة سيارات تريد ECU للمحرك:
    │
    ▼
تتعاقد مع مورّد A
    │
    ▼
المورّد يكتب الكود بطريقته الخاصة
مع مكتباته الخاصة
مع طبقة تجريد عتادية خاصة به
    │
    ▼
بعد 5 سنوات تريد تغيير المورّد إلى B
    │
    ▼
كل الكود يجب إعادة كتابته من الصفر!
```

أيضاً:

```
المهندس الذي يعمل على ECU المحرك:
- يحتاج يعرف تفاصيل chip الـ Microcontroller
- يحتاج يعرف تفاصيل حساسات الضغط والحرارة
- يحتاج يعرف بروتوكولات الشبكة
- ثم يكتب منطق المحرك نفسه

كل هذا في ملفات كود ضخمة ومتشابكة
```

هذا يُسمى: Spaghetti Code (كود السباغيتي).

```
function controlEngine() {
   // مباشرة يكتب لسجلات الـ Hardware
   *REGISTER_0x4000 = 0xFF;
   
   // مباشرة يقرأ من CAN
   canRead(&msg);
   
   // منطق المحرك
   if (RPM > 3000) {
      // ...
   }
}
```

كل شيء مخلوط ومتداخل.

AUTOSAR يفصل هذا بشكل جميل ومنظم.

## الجزء الثالث: معمارية AUTOSAR

### الصورة الكبيرة أولاً

AUTOSAR يقسّم البرنامج داخل ECU إلى طبقات:

```
┌────────────────────────────────────────────────────────────┐
│                APPLICATION LAYER                           │
│              طبقة التطبيقات (SWCs)                        │
│   ┌──────────┐  ┌──────────┐  ┌──────────┐  ┌──────────┐  │
│   │  SWC 1   │  │  SWC 2   │  │  SWC 3   │  │  SWC N   │  │
│   │ المحرك  │  │الانبعاث  │  │ التبريد  │  │  .....   │  │
│   └──────────┘  └──────────┘  └──────────┘  └──────────┘  │
├────────────────────────────────────────────────────────────┤
│                    RTE                                     │
│           (Runtime Environment)                            │
│        بيئة التشغيل — الوسيط الذكي                       │
├────────────────────────────────────────────────────────────┤
│               BSW - Basic Software                         │
│              البرمجيات الأساسية                           │
│  ┌─────────────────────────────────────────────────────┐   │
│  │              Service Layer (طبقة الخدمات)           │   │
│  ├─────────────────────────────────────────────────────┤   │
│  │           ECU Abstraction Layer (تجريد ECU)         │   │
│  ├─────────────────────────────────────────────────────┤   │
│  │          MCAL (تجريد الـ Microcontroller)           │   │
│  └─────────────────────────────────────────────────────┘   │
├────────────────────────────────────────────────────────────┤
│                  HARDWARE                                  │
│               العتاد (Microcontroller)                    │
└────────────────────────────────────────────────────────────┘
```

الفكرة الجوهرية:

```
SWC (التطبيق) لا تعرف أي ECU تشتغل عليه.
لا تعرف أي Microcontroller.
لا تعرف أي حساس بالضبط.

تتكلم فقط مع RTE.
والـ RTE يرتّب الباقي.
```

هذا هو سر قوة AUTOSAR.

---

### الخطوة الرابعة: SWC (مكوّن البرنامج)

SWC = Software Component (مكوّن البرنامج).

هو الجزء الذي يكتبه المهندس الوظيفي.

تخيل أنك موظف جديد في شركة.

```
أنت (SWC):
- تفعل مهمة محددة (منطق المحرك)
- تتحدث مع الشركة عبر واجهة محددة (الـ Port)
- لا تعرف كيف تعمل الشركة من الداخل
- لا تعرف من يعمل في الأقسام الأخرى
- فقط تستقبل وترسل معلومات عبر بريد الشركة (RTE)
```

**بنية الـ SWC:**

```
┌─────────────────────────────────────────────────┐
│                    SWC                          │
│                                                 │
│   Port (منفذ)                Port (منفذ)        │
│   ┌──────────┐              ┌──────────┐        │
│   │  P-Port  │              │  R-Port  │        │
│   │ (مُرسِل) │              │ (مستقبِل)│        │
│   └──────────┘              └──────────┘        │
│           │                      ↑              │
│           │    ┌──────────┐      │              │
│           └───►│ Runnable │──────┘              │
│                │ (دالة)   │                     │
│                └──────────┘                     │
│                                                 │
│   C/S Port (منفذ العميل/الخادم)                │
│   ┌──────────┐                                  │
│   │ Client   │ ← يطلب خدمة من SWC آخر          │
│   │ Port     │                                  │
│   └──────────┘                                  │
└─────────────────────────────────────────────────┘
```

**أنواع السWCs:**

```
1. Application SWC (مكوّن التطبيق):
   ← يحتوي منطق العمل الفعلي
   ← مثل: خوارزمية التحكم في المحرك

2. Sensor Actuator SWC (مكوّن الحساس/المشغّل):
   ← يقرأ من الحساسات مباشرة
   ← يكتب للمشغّلات مباشرة
   ← يعيش قريباً من العتاد

3. Composition SWC (مكوّن التجميع):
   ← يجمع عدة SWCs ويمثّلها ككتلة واحدة
   ← مثل "نظام المحرك" يضم عدة SWCs صغيرة

4. Service SWC (مكوّن الخدمة):
   ← يقدم خدمة لـ SWCs أخرى
   ← مثل خدمة Diagnostic
```

---

### الخطوة الخامسة: Port و Interface

**Port (المنفذ):**

هو نقطة الاتصال بين SWC والعالم الخارجي.

```
مثل مقبس الكهرباء في الحائط:
- مكوّن P-Port يبث البيانات (مثل مقبس مُزوّد)
- مكوّن R-Port يستقبل البيانات (مثل مقبس مستهلك)
```

**Interface (الواجهة):**

يعرّف شكل البيانات التي تمرّ عبر الـ Port.

```
مثال: واجهة "سرعة الدوران"
تعرّف:
- اسم العنصر: EngineSpeed
- النوع: uint16
- الوحدة: RPM
- النطاق: 0 - 8000
```

**أنواع Interfaces:**

```
1. Sender-Receiver Interface (مُرسِل-مستقبِل):
   ← لبث البيانات أحادية الاتجاه
   ← مثل: بث قيمة درجة الحرارة

2. Client-Server Interface (عميل-خادم):
   ← لاستدعاء الدوال عن بُعد
   ← مثل: "أحسب لي قيمة حقن الوقود"
   ← لها رد (نتيجة)

3. Mode-Switch Interface (واجهة تبديل الوضع):
   ← لتغيير أوضاع التشغيل
   ← مثل: الانتقال من وضع "التشغيل" لوضع "النوم"
```

### الخطوة السادسة: VFB (الناقل الوظيفي الافتراضي)

قبل أن نفهم الـ RTE، يجب أن نفهم مفهوماً أعمق وأجمل منه.

VFB = Virtual Function Bus (الناقل الوظيفي الافتراضي).

هذا هو السؤال الجوهري:

```
عندما يصمّم المهندس SWC_EngineControl وSWC_FuelInjection...

هل يحتاج أن يعرف:
- في أي ECU ستعيش كل SWC؟
- عبر أي بروتوكول سيتواصلان؟  (CAN؟ LIN؟)
- كم عدد الـ ECUs في السيارة؟

الجواب: لا — وهذه هي عبقرية الـ VFB.
```

**فكرة الـ VFB:**

تخيّل أن كل SWCs في السيارة كلها موصولة بناقل واحد افتراضي ضخم.

```
┌─────────────────────────────────────────────────────────────────┐
│                    السيارة كلها                                 │
│                                                                 │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐  ┌──────────┐        │
│  │ SWC      │  │ SWC      │  │ SWC      │  │ SWC      │        │
│  │ Engine   │  │ Fuel     │  │ Airbag   │  │ Instrument│        │
│  └────┬─────┘  └────┬─────┘  └────┬─────┘  └────┬─────┘        │
│       │             │             │             │               │
│  ═════╪═════════════╪═════════════╪═════════════╪═════          │
│            VFB (Virtual Function Bus)                           │
│            الناقل الوظيفي الافتراضي                            │
│                   (مفهوم — لا يوجد فعلياً في الكود)            │
└─────────────────────────────────────────────────────────────────┘
```

**مرحلتان: التصميم ثم التنفيذ**

```
مرحلة التصميم (Design Time):
    SWC_EngineControl ───VFB──► SWC_FuelInjection
    المهندس يقول: "هذان السWC يتبادلان سرعة الدوران"
    لا يهتم بأي ECU، لا بأي بروتوكول
    ↓
    ↓ يُقرَّر لاحقاً: أين تعيش كل SWC؟
    ↓

مرحلة التنفيذ (Runtime):
    الحالة 1: كلاهما في نفس ECU
    SWC_EngineControl ───RTE──► SWC_FuelInjection
    الـ RTE ينسخ القيمة في الذاكرة المشتركة
    ↓
    الحالة 2: في ECUs مختلفة
    SWC_EngineControl ───RTE──CAN──RTE──► SWC_FuelInjection
    الـ RTE يُوصّل عبر شبكة CAN
```

**الخلاصة:**

```
VFB = الفكرة (مرحلة التصميم)
RTE = التطبيق الفعلي (مرحلة التنفيذ على ECU محددة)

VFB يجعل المهندس يفكّر في الوظيفة فقط.
RTE يُنفّذ هذا التواصل على أرض الواقع.
```

هذا هو الفصل الذكي بين التصميم والتنفيذ في AUTOSAR.

---

### الخطوة السابعة: RTE (بيئة التشغيل)

RTE = Runtime Environment (بيئة التشغيل).

هو قلب AUTOSAR.

**تخيّله كمدير حكيم وسط الشركة:**

```
SWC A يريد أن يرسل قيمة لـ SWC B
    │
    ▼
SWC A يستدعي: Rte_Write_Port_Variable(value)
    │
    ▼
RTE يأخذ القيمة ويسلّمها لـ SWC B
    │
    ▼
SWC B تستقبلها بـ: Rte_Read_Port_Variable(&value)
```

SWC A لا تعرف أين تعيش SWC B.

هل في نفس الـ ECU أم في ECU أخرى؟

الـ RTE يعرف ويهتم.

**مهام الـ RTE:**

```
1. نقل البيانات بين SWCs:
   ← إذا في نفس ECU: نسخ مباشر في الذاكرة
   ← إذا في ECUs مختلفة: عبر CAN أو LIN

2. جدولة تنفيذ الـ Runnables:
   ← "Runnable هذا يُشغَّل كل 10ms"
   ← "Runnable هذا يُشغَّل عند حدوث حدث"

3. إدارة البيانات:
   ← Queue (طابور) للبيانات المتراكمة
   ← Last-Value لآخر قيمة مُرسَلة

4. استدعاء خدمات BSW:
   ← يوفّر واجهة نظيفة للـ SWC للوصول لـ BSW
```

**كيف يُولَّد الـ RTE؟**

الـ RTE لا يُكتب يدوياً!

يُوصَف النظام بملفات XML، ثم أداة توليد تنتج كود C تلقائياً.

```
.arxml ملفات (وصف النظام)
    │
    ▼
RTE Generator (مولّد الـ RTE)
    │
    ▼
كود C جاهز للترجمة (Rte.c, Rte.h)
```

هذا اسمه: Code Generation (توليد الكود).

## الجزء الرابع: BSW (البرمجيات الأساسية)

### ما هو BSW؟

BSW = Basic Software (البرمجيات الأساسية).

هي مجموعة الطبقات التي تجلس تحت الـ RTE.

تخيّلها كطاقم الموظفين خلف الكواليس:

```
أنت (SWC) تضغط زر "أضاء المصباح"
    │
    ▼
RTE يرسل الطلب
    │
    ▼
BSW:
    - Service Layer تستلم الطلب
    - ECU Abstraction تقوله "أي منفذ GPIO؟"
    - MCAL تُفعّل المنفذ الفيزيائي فعلاً
```

### MCAL (طبقة تجريد المتحكم الدقيق)

MCAL = Microcontroller Abstraction Layer.

هذه أدنى طبقة برمجية فوق العتاد مباشرة.

```
تخيّل أنك تريد قراءة جهد كهربائي من حساس:

بدون MCAL (الطريقة القديمة):
ADC_REGISTER_0x4001 = ADC_START_BIT;
while (!(ADC_REGISTER_0x4002 & ADC_DONE));
value = ADC_REGISTER_0x4003;

مع MCAL (الطريقة AUTOSAR):
Adc_StartGroupConversion(AdcGroup_Temp);
Adc_ReadGroup(AdcGroup_Temp, &buffer);
```

الكود العلوي لا يعرف أي سجل في أي عنوان.

**مكوّنات MCAL الرئيسية:**

```
ADC Driver (مشغّل محوّل القيم التناظرية-الرقمية):
← يقرأ من الحساسات التناظرية
← الجهد، الحرارة، الضغط...

PWM Driver (مشغّل تعديل عرض النبضة):
← يتحكم في المحركات والمشغّلات
← يُستخدم لضبط الصمامات والمضخات

DIO Driver (مشغّل I/O الرقمي):
← منافذ رقمية (تشغيل/إيقاف)
← LEDs، مفاتيح...

SPI Driver (مشغّل الواجهة التسلسلية):
← اتصال مع ICs خارجية
← شاشات، ذاكرة خارجية...

CAN Driver (مشغّل شبكة CAN):
← يُرسل ويستقبل رسائل CAN
← التطبيق الأساسي في السيارات

LIN Driver (مشغّل شبكة LIN):
← للأجهزة البطيئة والرخيصة

FlexRay Driver (مشغّل FlexRay):
← للأنظمة الحرجة بالوقت

Eth Driver (مشغّل Ethernet):
← للسيارات الحديثة

ICU Driver (مشغّل وحدة الإدخال والتقاط):
← يقيس الترددات والنبضات
← مثل: قراءة حساسات السرعة من الإشارة المربعة

GPT Driver (مشغّل مؤقت الأغراض العامة):
← إدارة الأجهزة الزمنية في الـ MCU

MCU Driver (مشغّل وحدة MCU):
← تهيئة ساعة الـ Microcontroller
← إدارة أوضاع الطاقة
```

### ECU Abstraction Layer (طبقة تجريد ECU)

تجلس فوق MCAL مباشرة.

تُخفي تفاصيل التوصيل الفيزيائي.

```
مثال: قراءة درجة حرارة ماء المحرك

MCAL تعرف:
"الحساس متصل بـ ADC القناة 3 في الـ MCU"

ECU Abstraction تعرف:
"درجة حرارة الماء هي هذا الحساس"

السWC تطلب فقط:
"أعطني قراءة درجة حرارة الماء"
```

**مكوّنات ECU Abstraction:**

```
IoHwAb (I/O Hardware Abstraction):
← يُجرّد الحساسات والمشغّلات
← بدلاً من "ADC قناة 3" تقول "درجة حرارة الماء"

Complex Drivers (مشغّلات معقدة):
← لأجهزة لا تناسب التجريد القياسي
← مثل: مشغّل محرك BLDC خاص

Watchdog Manager (مدير كلب الحراسة):
← يُشغّل دوائر الحراسة في الـ MCU
← يُعيد تشغيل النظام إذا تجمّد
```

### Service Layer (طبقة الخدمات)

أعلى طبقة في BSW.

تُقدّم خدمات عالية المستوى للـ RTE والـ SWCs.

```
تخيّلها كالإدارات الرئيسية في شركة كبيرة:
- إدارة المالية (OS)
- إدارة الاتصالات (COM Stack)
- إدارة الأرشيف (Memory Stack)
- إدارة الجودة (Diagnostic)
- إدارة الأمن (Security)
```

**أهم مكوّنات Service Layer:**

---

#### OS (نظام التشغيل)

نظام تشغيل مُصمَّم خصيصاً للأنظمة الزمنية الحقيقية.

```
يعتمد على OSEK/VDX:
← معيار قديم ومجرَّب
← حتمي: Task ذو أولوية أعلى يعمل في وقته دائماً
← ليس مثل Windows الذي يقرر هو متى يُشغّل البرامج
```

مفاهيم OS في AUTOSAR:

**Task (المهمة):**

```
وحدة التنفيذ الأساسية:

TASK(EngineControlTask) {
   // يُشغَّل كل 10ms
   ReadSensors();
   ComputeFuelInjection();
   SetActuators();
}

أنواع المهام:
- Basic Task (مهمة أساسية): تعمل وتنتهي
- Extended Task (مهمة ممتدة): تستطيع الانتظار لحدث
```

**Priority (الأولوية):**

```
مهمة الفرامل     ← أولوية 255 (الأعلى)
مهمة المحرك     ← أولوية 100
مهمة الإضاءة    ← أولوية 10  (الأدنى)

إذا جاءت مهمة الفرامل أثناء مهمة الإضاءة:
← مهمة الإضاءة تتوقف فوراً
← الفرامل تُنفَّذ
← الإضاءة تكمل من حيث توقفت
```

هذا اسمه: Preemption (الاستباق).

**Alarm (التنبيه):**

```
يُشغّل Task بشكل دوري تلقائياً:

Alarm: "كل 10ms شغّل EngineControlTask"
```

**Schedule Table (جدول الجدولة):**

```
بديل أكثر مرونة من الـ Alarm:
يُمكن تشغيل عدة Tasks في توقيتات دقيقة:

زمن 0ms    → شغّل SensorReadTask
زمن 2ms    → شغّل ControlTask
زمن 5ms    → شغّل ComTask
زمن 10ms   → شغّل SensorReadTask مرة أخرى
...وهكذا
```

---

#### COM (Communication Stack / مجموعة الاتصالات)

يُدير الاتصال بين ECUs.

```
SWC تريد إرسال "سرعة المحرك = 3000 RPM" عبر CAN
    │
    ▼
SWC تستدعي RTE
    │
    ▼
RTE يستدعي COM
    │
    ▼
COM يُجمّع البيانات في رسالة CAN
    │
    ▼
PDU Router يوجّه الرسالة للشبكة الصحيحة
    │
    ▼
CAN Interface تُمرّر لـ CAN Driver
    │
    ▼
CAN Driver يرسل على شبكة CAN الفيزيائية
```

**طبقات COM Stack:**

```
┌─────────────────────────────────────────────────────────┐
│  COM (Communication Manager / مدير الاتصالات)           │
│  ← يدير الإشارات والـ PDUs على مستوى التطبيق           │
├─────────────────────────────────────────────────────────┤
│  PDU Router (موجّه وحدات بيانات البروتوكول)             │
│  ← يوجّه الرسائل بين طبقات الاتصال                    │
├─────────────────────────────────────────────────────────┤
│  TP (Transport Protocol / بروتوكول النقل)               │
│  ← لتقسيم الرسائل الكبيرة إلى رسائل CAN صغيرة         │
│  ← مثل UDS Diagnostic                                   │
├─────────────────────────────────────────────────────────┤
│  CAN Interface / LIN Interface / FlexRay Interface      │
│  ← واجهة موحدة بغض النظر عن البروتوكول                │
├─────────────────────────────────────────────────────────┤
│  CAN Driver / LIN Driver / FlexRay Driver               │
│  ← MCAL: يتحدث مع العتاد الفيزيائي                    │
└─────────────────────────────────────────────────────────┘
```

---

#### Memory Stack (مجموعة إدارة الذاكرة)

يُدير الذاكرة غير المتطايرة (تبقى حتى بعد إيقاف السيارة).

```
مثال للاستخدام:
- حفظ أكواد الأعطال (Diagnostic Trouble Codes)
- حفظ إعدادات المستخدم (مستوى صوت الراديو)
- حفظ بيانات المعايرة (Calibration Data)
```

**طبقات Memory Stack:**

```
NvM (Non-volatile Memory Manager / مدير الذاكرة غير المتطايرة):
← واجهة موحدة لحفظ واسترجاع البيانات

MemIf (Memory Interface / واجهة الذاكرة):
← يوجّه بين Fee و Ea

Fee (Flash EEPROM Emulation / محاكاة EEPROM في الفلاش):
← يُحاكي EEPROM فوق ذاكرة Flash الداخلية

Ea (EEPROM Abstraction / تجريد EEPROM):
← للـ EEPROM الخارجية

Fls (Flash Driver / مشغّل الفلاش):
← يكتب ويقرأ من ذاكرة Flash الداخلية (MCAL)

Eep (EEPROM Driver / مشغّل EEPROM):
← للـ EEPROM الخارجية (MCAL)
```

**مثال عملي:**

```
السيارة تُشغَّل:
    │
    ▼
NvM تقرأ إعدادات المستخدم من Flash
    │
    ▼
أثناء التشغيل يحدث عطل:
    │
    ▼
DEM يطلب من NvM حفظ كود العطل
    │
    ▼
NvM تكتب في Fee → Fee في Fls → Fls في Flash الفيزيائية
    │
    ▼
بعد 3 أشهر الميكانيكي يوصل أداة الـ Diagnostic:
    │
    ▼
يقرأ كود العطل من الذاكرة
```

---

#### Diagnostic Stack (مجموعة التشخيص)

هذا ما يستخدمه الميكانيكي عندما يوصل الكمبيوتر بالسيارة.

```
UDS = Unified Diagnostic Services
(خدمات التشخيص الموحدة)

الميكانيكي يقول:
"أعطني كل أكواد الأعطال المحفوظة"
    │
    ▼
DCM يستقبل الطلب
    │
    ▼
DCM يسأل DEM
    │
    ▼
DEM يُرجع قائمة الأعطال
    │
    ▼
DCM يُرسلها للميكانيكي
```

**المكوّنات:**

```
DCM (Diagnostic Communication Manager / مدير اتصالات التشخيص):
← يفهم بروتوكول UDS (ISO 14229)
← يستقبل طلبات التشخيص ويرد عليها
← مثل: قراءة قيم الحساسات مباشرة

DEM (Diagnostic Event Manager / مدير أحداث التشخيص):
← يُسجّل الأعطال ويحفظها
← كل عطل له: كود (DTC) + سياق + عداد تكرار
← DTC = Diagnostic Trouble Code (كود عطل التشخيص)

FiM (Function Inhibition Manager / مدير تعطيل الوظائف):
← إذا حدث عطل في حساس ما
← FiM يُعطّل الوظائف التي تعتمد عليه
← تجنباً للنتائج الخاطئة
```

**أمثلة على رموز UDS:**

```
0x22 → اقرأ قيمة بيانات بـ Identifier
0x23 → اقرأ من الذاكرة مباشرة
0x27 → طلب بذرة الأمان (Security Access)
0x2E → اكتب قيمة بيانات
0x10 → افتح جلسة تشخيص
0x11 → أعد تشغيل ECU
0x14 → امسح أكواد الأعطال
0x19 → اقرأ أكواد الأعطال
0x34 → ابدأ تحميل برنامج جديد
0x36 → نقل بيانات البرنامج
0x37 → أنهِ نقل البيانات
```

## الجزء الخامس: الاتصال داخل AUTOSAR

### كيف تتواصل SWCs مع بعضها؟

**السيناريو 1: SWCs في نفس ECU:**

```
SWC_EngineControl يريد إرسال قيمة لـ SWC_FuelInjection

استدعاء: Rte_Write_EngineControl_EngineSpeed(3000)
    │
    ▼
RTE ينسخ القيمة في buffer مشترك في الذاكرة
    │
    ▼
SWC_FuelInjection تستدعي: Rte_Read_FuelInjection_EngineSpeed(&speed)
    │
    ▼
RTE يُرجع القيمة من الـ buffer
```

سريع جداً. نسخ مباشر في الـ RAM.

**السيناريو 2: SWCs في ECUs مختلفة:**

```
SWC_EngineControl في ECU1 يريد إرسال قيمة لـ SWC_Instrument في ECU2

استدعاء: Rte_Write_EngineControl_EngineSpeed(3000)
    │
    ▼
RTE في ECU1 → COM → CAN Interface → CAN Driver
    │
    ▼
شبكة CAN
    │
    ▼
CAN Driver في ECU2 → CAN Interface → COM → RTE في ECU2
    │
    ▼
SWC_Instrument.Rte_Read_EngineSpeed(&speed) تحصل على القيمة
```

بالنسبة للـ SWCs: نفس الاستدعاء تماماً.
البنية التحتية هي التي تختلف.

هذا جمال AUTOSAR.

### Runnable (الروتين القابل للتشغيل)

Runnable هو الدالة الأساسية داخل SWC.

```
مثال SWC للتحكم في درجة الحرارة:

AUTOSAR SWC: ThermalControl
    │
    ├── Runnable: ReadTemperature (يُشغَّل كل 20ms)
    │   ← يقرأ قيمة درجة الحرارة من الـ Port
    │
    ├── Runnable: ControlFan (يُشغَّل كل 50ms)
    │   ← يقرر هل يُشغّل المروحة أم لا
    │
    └── Runnable: EmergencyShutdown (يُشغَّل عند حدث)
        ← يُغلق المحرك إذا الحرارة خطرة جداً
```

**أنواع تفعيل الـ Runnables:**

```
1. Timing Event (حدث زمني):
   ← كل X مللي ثانية
   ← "شغّل ReadSensors كل 10ms"

2. Data Received Event (حدث استقبال بيانات):
   ← عند وصول بيانات جديدة
   ← "شغّل ProcessData عند وصول رسالة جديدة"

3. Init Event (حدث التهيئة):
   ← مرة واحدة عند بدء تشغيل النظام
   ← "شغّل InitSystem عند الإقلاع"

4. Swc Mode Switch Event (حدث تغيير الوضع):
   ← عند تغيير وضع النظام
   ← "شغّل EnterSleep عند الانتقال لوضع Sleep"

5. Background Event (حدث الخلفية):
   ← عندما لا توجد مهام أخرى
   ← أدنى أولوية ممكنة
```

---

### Runnable إلى OS Task — السؤال المفضّل في المقابلات

هنا يقع كثير من المهندسين في خطأ مفاهيمي شهير:

```
الخطأ الشائع:
"الـ OS يُشغّل الـ Runnable مباشرة"

الصواب:
الـ OS لا يعرف أي Runnable.
الـ OS يعرف فقط Tasks.
```

**الفرق الجوهري:**

```
Runnable = دالة C عادية داخل SWC
           مثل: void FuelControl_Calculate(void)
           لا تملك وقت CPU خاص بها
           لا تُجدول مباشرة من OS

OS Task  = وحدة التنفيذ الفعلية
           تملك Stack خاص بها
           لها أولوية محددة في OS
           الـ OS يُجدولها ويمنحها الـ CPU
```

**إذن كيف يعمل هذا؟**

```
الـ RTE هو الجسر:

OS Task يبدأ
    │
    ▼
SchM (Schedule Manager) يُدير الترتيب
    │
    ▼
RTE يستدعي Runnable_A()
    │ (Runnable تنفّذ وتنتهي)
    ▼
RTE يستدعي Runnable_B()
    │ (Runnable تنفّذ وتنتهي)
    ▼
OS Task ينتهي
```

**مثال حقيقي — Mapping في الـ AUTOSAR Configuration:**

```
OS Task: Engine_10ms_Task
├── Priority: 100
├── Period: 10ms
└── يحتوي:
    ├── Runnable: SensorManager_Read      ← من SWC_SensorManager
    ├── Runnable: FuelControl_Calculate   ← من SWC_FuelControl
    └── Runnable: NetworkManager_Send     ← من SWC_NetworkManager

OS Task: Safety_5ms_Task
├── Priority: 200  (أعلى ← تستبق Engine_10ms_Task)
├── Period: 5ms
└── يحتوي:
    └── Runnable: BrakeControl_Monitor    ← من SWC_BrakeControl
```

**ماذا يعني هذا في الممارسة؟**

```
1. Runnable واحد يمكن أن يكون في Task بأولوية عالية
   لأنه حرج (مثل Brake Monitor)

2. عدة Runnables غير حرجة تُجمَع في Task واحد
   لتوفير overhead الـ Context Switching

3. Runnable لا تعرف في أي Task تعيش
   يُحدَّد ذلك في الـ Configuration خارج الكود

4. نفس الـ SWC يمكن أن يكون لها Runnables
   في Tasks مختلفة بأولويات مختلفة
```

**رسم المقارنة:**

```
┌─────────────────────────────────────────────────────────────────┐
│                          OS Scheduler                           │
│                        (مُجدوِل OS)                            │
│                                                                 │
│  ┌────────────────────────┐   ┌────────────────────────┐        │
│  │  Safety_5ms_Task       │   │  Engine_10ms_Task       │       │
│  │  Priority: 200         │   │  Priority: 100          │       │
│  │  ┌──────────────────┐  │   │  ┌──────────────────┐  │       │
│  │  │ Runnable:        │  │   │  │ Runnable:        │  │       │
│  │  │ BrakeControl_Mon │  │   │  │ SensorMgr_Read   │  │       │
│  │  └──────────────────┘  │   │  ├──────────────────┤  │       │
│  │                        │   │  │ Runnable:        │  │       │
│  │                        │   │  │ FuelCtrl_Calc    │  │       │
│  │                        │   │  └──────────────────┘  │       │
│  └────────────────────────┘   └────────────────────────┘        │
└─────────────────────────────────────────────────────────────────┘

                   ↑ هذا ما يراه ويُدير الـ OS فعلاً
```

**الخلاصة للمقابلة:**

```
"الـ Runnable ليست Thread ولا Task.
 إنها دالة C عادية تُستدعى من داخل Task.
 الـ OS يُجدول الـ Task.
 الـ RTE يُقرر أي Runnables تُستدعى وبأي ترتيب داخل الـ Task."
```

### Signal (الإشارة) و PDU و Message

مفاهيم مهمة في طبقة الاتصالات:

**Signal (الإشارة):**

```
أصغر وحدة بيانات ذات معنى
مثل: EngineSpeed (سرعة المحرك) - 16 بت - RPM
```

**PDU (Protocol Data Unit / وحدة بيانات البروتوكول):**

```
حاوية تجمع عدة Signals معاً:

PDU: EngineData
├── EngineSpeed (16 بت)
├── EngineTemp  (8 بت)
└── ThrottlePos (8 بت)
────────────────────
المجموع: 32 بت = 4 bytes في رسالة CAN
```

**CAN Frame (إطار CAN):**

```
┌────────────────────────────────────────────────────┐
│ ID (11 بت)  │ DLC (4 بت) │  Data (حتى 8 bytes)    │
│  0x123      │     4      │  [S1][S2][S3][ ][ ]    │
└────────────────────────────────────────────────────┘

ID  ← معرّف الرسالة (يحدد أولويتها على الشبكة)
DLC ← Data Length Code (طول البيانات)
Data ← البيانات الفعلية (PDU + Signals)
```

**كيف يُفكك COM الإشارات:**

```
رسالة CAN مُستقبَلة:
[0x0B, 0xB8, 0x50, 0x40]
    │
    ▼
COM يُفكك (Unpack):
- Byte 0-1: EngineSpeed = 0x0BB8 = 3000 RPM
- Byte 2:   EngineTemp  = 0x50   = 80°C
- Byte 3:   ThrottlePos = 0x40   = 25%
    │
    ▼
كل Signal يُرسَل لـ SWC المهتمة به
```

### الأمان في BSW

**Watchdog (كلب الحراسة):**

```
تخيّل حارس يمشي كل 10 ثوانٍ للتحقق من المخزن.
إذا لم يجد موظفاً يرد عليه خلال 10 ثوانٍ:
← يفترض أن هناك مشكلة
← يُنبّه المدير

الـ Watchdog يعمل نفس المبدأ:
- Software يُرسل "أنا بخير" كل X مللي ثانية
- إذا توقف عن الإرسال (تجمّد البرنامج)
← Watchdog يُعيد تشغيل ECU
```

في AUTOSAR:

```
WdgM (Watchdog Manager / مدير كلب الحراسة):
← يستلم "alive signals" من كل Runnable حرجة
← إذا لم يصله إشارة من أي منها في الوقت المحدد
← يُعطي أمر إعادة التشغيل عبر WdgDriver
```

**Memory Protection:**

```
كل Task له منطقة ذاكرة مُحددة.
لا يمكنه الكتابة خارجها.
إذا حاول:
← OS يُوقفه ويُسجّل خطأ
← لا يستطيع Task واحد إفساد ذاكرة Task آخر
```

---

### E2E Protection (الحماية من النهاية إلى النهاية)

مشكلة: بيانات CAN قد تتلف أثناء الإرسال.

```
المُرسِل يرسل: EngineSpeed = 3000 RPM

ضجيج كهرومغناطيسي على السلك:
يُغيّر بتاً في البيانات

المستقبِل يقرأ: EngineSpeed = 3064 RPM (خطأ!)
```

الحل: E2E (End-to-End Protection / الحماية من النهاية إلى النهاية).

```
المُرسِل يُضيف:
- CRC (Cyclic Redundancy Check / التحقق بالتكرار الدوري)
  ← مجموع تدقيق رياضي للبيانات
- Counter (عداد)
  ← رقم يزيد مع كل رسالة

المستقبِل يتحقق:
- هل الـ CRC صحيح؟ → البيانات سليمة
- هل الـ Counter في التسلسل الصحيح؟ → لم تُفقد رسالة
- إذا فشل أي منهما → تجاهل البيانات وأبلّغ DEM
```

### مثال عملي: SWC بسيطة

```c
/* ThermalControl_SWC.c */
/* هذا هو الكود الذي يكتبه المهندس */

#include "Rte_ThermalControl.h"  /* مُولَّد تلقائياً */

/* Runnable: يُشغَّل كل 20ms */
FUNC(void, THERMAL_CODE) ThermalControl_ReadAndControl(void)
{
    uint8 temperature;
    uint8 fanSpeed;

    /* قراءة درجة الحرارة عبر RTE */
    (void) Rte_Read_ThermalControl_TemperaturePort(&temperature);

    /* منطق التحكم */
    if (temperature > 90u) {
        fanSpeed = 100u;  /* مروحة بأقصى سرعة */
    }
    else if (temperature > 70u) {
        fanSpeed = 50u;   /* مروحة بنصف السرعة */
    }
    else {
        fanSpeed = 0u;    /* إيقاف المروحة */
    }

    /* إرسال أمر المروحة عبر RTE */
    (void) Rte_Write_ThermalControl_FanSpeedPort(fanSpeed);

    /* إذا الحرارة خطرة جداً - بلّغ عن عطل */
    if (temperature > 110u) {
        Dem_ReportErrorStatus(
            DemConf_DemEventParameter_OverTemperatureError,
            DEM_EVENT_STATUS_FAILED
        );
    }
}
```

لاحظ:

```
لا يوجد أي ذكر لـ:
- أي Microcontroller
- أي قناة ADC
- أي رسالة CAN
- أي عنوان في الذاكرة

فقط منطق التطبيق.
```

### AUTOSAR وأسئلة المقابلات

```
الأسئلة الأكثر شيوعاً:

1. ما الفرق بين SWC وBSW؟
   ← SWC: منطق التطبيق، لا يعرف العتاد
   ← BSW: برمجيات أساسية، تتعامل مع العتاد

2. ما دور الـ RTE؟
   ← الوسيط بين SWCs وBSW
   ← يُعرّيها من تفاصيل التواصل

3. ما الفرق بين P-Port وR-Port؟
   ← P-Port: Provided Port يُصدّر البيانات
   ← R-Port: Required Port يستورد البيانات

4. ما الفرق بين Sender-Receiver وClient-Server؟
   ← S-R: بث بيانات بدون رد مباشر
   ← C-S: طلب واستجابة (مثل استدعاء دالة)

5. ما هو MCAL ولماذا مهم؟
   ← طبقة تجريد العتاد الدنيا
   ← يُمكّن تبديل الـ MCU بسهولة

6. ما هو DEM ودوره؟
   ← يُسجّل الأعطال (DTCs)
   ← يحفظ السياق والتاريخ

7. كيف يختلف الـ AUTOSAR OS عن Windows/Linux؟
   ← AUTOSAR OS حتمي (Deterministic)
   ← مُضمَّن، لا متعدد مستخدمين
   ← أولويات ثابتة، Preemption مضمون

8. ما هو الـ Runnable وكيف يُفعَّل؟
   ← دالة داخل SWC يُشغّلها OS
   ← عبر: TimingEvent, DataReceivedEvent, InitEvent

9. ما هو الـ PDU وما علاقته بالـ Signal؟
   ← PDU يجمع Signals في وحدة نقل
   ← Signal هو عنصر البيانات ذو المعنى

10. ما الفرق بين Classical وAdaptive AUTOSAR؟
    ← Classical: موارد محدودة، حتمي، OS-OSEK
    ← Adaptive: موارد وفيرة، POSIX, SOME/IP, C++14

11. ما هو الـ VFB وما علاقته بالـ RTE؟
    ← VFB: مفهوم تصميمي — يتيح للمهندس وصف التواصل
      بين SWCs دون معرفة التوزيع على ECUs
    ← RTE: التنفيذ الفعلي لنفس التواصل على ECU محددة
    ← VFB في مرحلة التصميم → يتحول لـ RTE في مرحلة التنفيذ

12. ما الفرق بين Runnable وOS Task؟ وكيف يرتبطان؟
    ← Runnable: دالة C عادية داخل SWC، لا تُجدَّل مباشرة
    ← OS Task: وحدة التنفيذ، لها Stack وأولوية، يُجدولها الـ OS
    ← الـ RTE يستدعي الـ Runnables من داخل الـ OS Task
    ← Mapping يُعرَّف في الـ Configuration خارج الكود تماماً
```

## الجزء الثالث عشر: Cheat Sheet للمراجعة السريعة

### المفاهيم الجوهرية في 60 ثانية

```
AUTOSAR CP = معيار برمجة السيارات الكلاسيكي

الطبقات (من فوق لتحت):
SWC → RTE → BSW → Hardware

SWC = ما يكتبه المهندس (منطق فقط)
VFB = الناقل الافتراضي في مرحلة التصميم
RTE = الوسيط الفعلي (مُولَّد تلقائياً، تحقيق VFB)
BSW = كل شيء تحت الـ RTE
MCAL = أول طبقة فوق العتاد

التواصل:
P-Port يُرسل، R-Port يستقبل
S-R: بث بيانات (EngineSpeed، درجة حرارة)
C-S: طلب/استجابة (احسب شيئاً ما)

الاتصال بين ECUs:
CAN ← الأكثر شيوعاً
LIN ← بطيء ورخيص
FlexRay ← حتمي وسريع
Ethernet ← حديث وسريع جداً

Runnable ≠ OS Task:
Runnable = دالة C تُستدعى من Task
OS Task = ما يُجدوله ويُشغّله الـ OS فعلاً
الـ RTE يستدعي Runnables من داخل الـ Task

BSW الأهم:
OS ← جدولة Tasks
COM ← إرسال/استقبال Signals
NvM ← حفظ البيانات
DEM ← تسجيل الأعطال
DCM ← التشخيص (OBD2/UDS)
EcuM ← دورة حياة ECU

الأمان:
ISO 26262 ← معيار السلامة
ASIL D ← أعلى خطر (فرامل، توجيه)
E2E ← حماية البيانات أثناء الإرسال
Watchdog ← كشف تجمّد البرنامج

ملفات AUTOSAR:
.arxml ← وصف النظام بـ XML
```

---

### أسرع طريقة لتذكر الطبقات

```
تخيّل شطيرة من فوق لأسفل:

🍞  Application SWCs (الخبز العلوي)
    ← ما يأكله المستخدم (الوظيفة)

🥬  RTE (الخس)
    ← يُبقي الطبقات منفصلة

🍖  BSW Service Layer (اللحم)
    ← الخدمات الأساسية: OS, COM, Memory

🧀  ECU Abstraction (الجبن)
    ← يُخفي تفاصيل ECU

🍅  MCAL (الطماطم)
    ← مباشرة فوق العتاد

🍞  Hardware (الخبز السفلي)
    ← Microcontroller الفعلي
```

### التوصية النهائية للمهندس الباحث عن عمل

```
قبل المقابلة بأسبوع:
□ ارسم معمارية AUTOSAR من الذاكرة (SWC → RTE → BSW → HW)
□ اشرح الفرق بين MCAL وECU Abstraction وService بمثال
□ تدرّب على وصف دورة رسالة CAN كاملة من SWC إلى السلك

قبل المقابلة بيوم:
□ راجع مسرد المصطلحات
□ راجع Cheat Sheet
□ فكّر في مشروع قمت به وكيف توضّح فيه مفاهيم AUTOSAR

في المقابلة:
□ ابدأ دائماً بالصورة الكبيرة ثم تعمّق
□ ربط المفاهيم ببعض (RTE يحتاج SWC يحتاج Port يحتاج Interface)
□ اذكر لماذا القرار وليس فقط ماذا (لماذا MCAL وليس مباشرة؟)
□ اعترف بما لا تعرفه وقل كيف ستتعلمه

أهم جملة في المقابلة:
"AUTOSAR يفصل المنطق عن العتاد حتى نستطيع
 تغيير المورّد أو الـ MCU دون إعادة كتابة التطبيق"
```
